# Git Commit Policy

## 1. 작업과 커밋 단위

- 한 커밋은 독립적으로 설명하고 되돌릴 수 있는 논리적 변경 하나로 만듭니다.
- 해당 변경에 필요한 코드·테스트·문서·백로그 상태를 함께 포함합니다. 문서나 테스트라는 이유만으로 별도 커밋을 만들지 않습니다.
- 서로 무관한 기능·수정은 나눕니다. 기능 구현에 필요한 작은 정리는 함께 포함할 수 있고, 별도로 검토할 규모의 리팩터링은 분리합니다.
- 완료 기록에 현재 커밋의 해시를 넣기 위한 후속 커밋은 만들지 않습니다. 백로그 번호로 추적하고 기존 해시는 필요한 경우에만 보존합니다.
- 커밋을 허용받은 작업은 검증한 단위로 커밋합니다. 커밋 보류·금지 요청이 있으면 작업 트리에 유지하며, 나중에 나누기 위해 불필요한 중간 구현을 재구성하지 않습니다.

## 2. 개발 절차

1. 관련 문서·현재 코드·작업 트리 상태를 확인하고, 독립적으로 추적할 작업은 [백로그](./backlog.md)에 등록하거나 기존 항목을 갱신합니다.
2. 구현하고 변경에 맞는 검증을 수행합니다. 로직은 관련 테스트, UI는 실제 화면, 타입·빌드에 영향을 주면 해당 검사로 확인합니다. 단순 문서 수정은 링크·내용·diff 확인으로 충분합니다.
3. 최신 설계와 구현 문서를 필요한 만큼 갱신합니다. 완료 조건을 충족한 항목은 [완료 목록](./backlog-completed.md)으로 옮기고 결과만 짧게 기록합니다. 외부 검증이 남으면 완료 처리하지 않습니다.
4. staged diff에 해당 작업만 포함됐는지 확인하고 하나의 논리적 단위로 커밋합니다. 백로그 종료만을 위한 별도 커밋은 필요하지 않습니다.

## 3. 커밋 메시지

```text
[type] : <subject>

<body, optional>
```

| Type | 용도 |
|---|---|
| `[feat]` | 기능 추가·사용자 동작 개선 |
| `[fix]` | 버그 수정 |
| `[refactor]` | 동작 변화 없는 구조 정리 |
| `[docs]` | 문서만 수정 |
| `[test]` | 테스트만 추가·수정 |
| `[style]` | 포맷 등 비기능적 수정 |
| `[perf]` | 성능 개선 |
| `[chore]` | 의존성·설정·버전 관리 |
| `[build]`, `[ci]`, `[deploy]`, `[revert]`, `[content]` | 빌드·CI·배포·되돌리기·콘텐츠 변경 |

- 제목은 영어 명령형, 최대 50자, 끝에 마침표 없이 구체적으로 씁니다. 파일명·함수명 같은 식별자는 번역하지 않습니다.
- 본문은 필요한 경우에만 무엇을 왜 바꿨는지와 중요한 검증·제약을 적고 줄당 72자 이하로 씁니다.
- 기능에 딸린 테스트·문서는 주된 변경의 type을 사용합니다. 예: `[feat] : Add walking rewards`에 구현·테스트·설계·백로그 갱신을 함께 포함.
- 관련 번호는 diff에 포함된 경우 `[Issue]: I-034`처럼 본문 아래에 기록할 수 있습니다. 호환성이 깨지면 `BREAKING CHANGE:`에 영향과 대응을 적습니다.
- 이름·이메일 등 개인정보, 비밀 값, `.env` 변경은 포함하지 않습니다. staged 변경만 커밋합니다.
- `Co-Authored-By`, `Claude-Session` 트레일러는 추가하지 않습니다.

## 4. 버전과 CHANGELOG

2026-11-14 정식 공개부터 `1.0.0`입니다(그 전은 `0.x.y`). 푸터는 `package.json`의 버전을 표시합니다.

- 개발 중 사용자에게 의미 있는 변경은 [CHANGELOG](../CHANGELOG.md)의 `Unreleased`에 짧게 모읍니다. 관련 구현 커밋에 포함하며 순수 문서·내부 정리마다 항목을 만들 필요는 없습니다.
- **배포하거나 사용자가 명시적으로 버전을 확정할 때 변경 묶음마다 한 번** 올립니다. 일반 커밋 요청·백로그 항목 완료만으로 버전을 올리지 않습니다.
- 기능 추가·개선이 포함된 묶음은 minor, 버그 수정만 있는 묶음은 patch를 올립니다. 문서·리팩터링·테스트만 바뀌면 그대로 둡니다. 여러 기능·버그가 함께 있어도 가장 큰 변경 기준으로 한 번만 올립니다.
- 확정할 때 develop에서 `npm version minor --no-git-tag-version` 또는 `patch`로 `package.json`과 `package-lock.json`을 함께 갱신하고, `Unreleased` 내용을 해당 버전·날짜 아래로 옮깁니다. 다음 변경을 위한 빈 `Unreleased` 구역은 유지합니다.
- 버전·CHANGELOG를 한 번의 릴리스 커밋에 묶을 수 있습니다. 예: `[chore] : Release 0.23.0`. 항목마다 기능 → 버전 → 백로그 종료의 3단계 커밋을 만들지 않습니다.
- 기존 버전과 커밋 이력은 다시 쓰지 않습니다.
- 배포: 릴리스 커밋을 develop에서 만들고 master로 fast-forward한 뒤, master의 그 커밋에 `v1.0.0` 같은 버전 태그(annotated)를 답니다. master에 푸시하면 Vercel이 운영 사이트를 배포합니다. `1.0.0` 이전 버전에는 태그가 없습니다.
