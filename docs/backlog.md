# 버그·개선 백로그

사용하면서 발견한 **버그**와 **개선 아이디어**를 모아두는 곳입니다.
접수는 별도 대화에서 받고, 개발 대화에서는 이 파일을 보고 처리합니다.

## 처리 규칙

- 새 항목은 `열림` 상태로 맨 아래에 추가하고, 번호는 이어서 매깁니다. (`B` 버그, `I` 개선)
- 개발 쪽에서 작업을 시작하면 `진행 중`, 끝나면 `완료`로 바꾸고 커밋 해시를 적습니다.
- 하지 않기로 한 항목은 `보류`로 바꾸고 이유를 한 줄 남깁니다.
- 우선순위: `높음`(쓰는 데 지장) · `보통` · `낮음`(있으면 좋음)

### I-002 · 자동 시작 시 완료 팝업을 5초 보여주고 닫힌 뒤 다음 세션 시작
- 종류: 개선
- 우선순위: 보통
- 상태: 완료
- 등록일: 2026-11-08
- 화면/기능: 설정의 "휴식 자동 시작", "집중 자동 시작" / 세션 완료 팝업(`CompletionDialog`)
- 내용: 지금은 자동 시작이 켜져 있으면 세션이 끝나는 순간 다음 세션이 바로 시작되고, 완료 팝업은 "확인"을 누를 때까지 떠 있다. 팝업이 열려 있는 동안 이미 다음 세션 시간이 흐르고, 팝업을 직접 닫아야 한다.
- 기대 동작 (자동 시작이 켜져 있을 때):
  1. 세션이 끝나면 완료 팝업이 자동으로 뜬다.
  2. 팝업에 남은 시간을 보여준다. 예: "5초 후 휴식 시작", "5초 후 집중 시작" (1초마다 줄어듦)
  3. 5초가 지나면 팝업이 저절로 닫히고, **그때부터** 다음 세션이 시작된다. 팝업이 떠 있는 5초 동안 다음 세션 시간은 흐르지 않는다.
  4. 카운트다운 중 팝업에 버튼 두 개를 둔다.
     - **지금 시작**: 기다리지 않고 바로 다음 세션을 시작하고 팝업을 닫는다.
     - **취소**: 이번에는 자동 시작하지 않는다. 팝업을 닫고 다음 세션은 시작 전 상태로 둔다. (자동 시작 설정 자체는 그대로 켜져 있음)
  5. 자동 시작이 꺼져 있을 때의 팝업("나중에", "OO 시작 →")은 지금과 같다.
- 관련 코드:
  - `src/features/timer/timer.ts`: `shouldAutoStart()`와 세션 완료 처리 부분. 지금은 자동 시작이면 다음 세션의 끝나는 시각을 이전 세션이 끝난 시각(`endedAt`) 기준으로 잡아 바로 running 상태로 만든다. 5초 대기 상태(예: `status: "starting"` 또는 `startsAt`)를 추가하거나, 시작 시각을 `endedAt + 5초`로 미루는 방식이 필요하다.
  - `src/features/timer/components/CompletionDialog.tsx`: `nextIsRunning`일 때 "확인" 버튼과 "OO이 자동으로 시작됐어요." 안내를 보여주는 부분을 카운트다운으로 바꾼다.
  - 같은 파일의 `useDelayedOpen`: 집중 완료 시 축하 효과 때문에 팝업이 1초 늦게 열린다(움직임 줄이기 설정이면 바로).
  - `src/features/timer/timer.test.ts`, `store.test.ts`: 자동 시작 관련 테스트 수정 필요.
- 개발 시 확인할 점:
  - **5초 기준 시각:** `setTimeout`이 아니라 시각 기준(예: `endedAt + 대기 시간`)으로 계산해야 한다. 탭이 백그라운드에 있으면 타이머 호출이 늦어지고, 자리를 비운 사이 끝난 경우의 기존 규칙(다음 세션까지 이미 끝났으면 시작 전 상태로 둠)과도 맞아야 한다.
  - **축하 지연 1초:** 팝업이 1초 늦게 열리므로, 5초를 팝업이 열린 시점부터 셀지(사용자가 5초를 온전히 봄) 세션이 끝난 시점부터 셀지 정해야 한다. 제안: 팝업이 열린 시점부터.
  - **취소 이후 상태:** 취소하면 다음 세션은 처음부터 시작 전(대기) 상태여야 한다. 대기 중 흘러간 시간이 빠지면 안 된다.
  - **X·Esc·바깥 클릭으로 닫을 때:** "취소"와 같게 처리하는 것이 자연스럽다. (실수로 닫아도 시간이 몰래 흐르지 않도록)
  - **팝업 안의 다른 기능:** 집중 완료 팝업에는 할 일 완료 체크(`TaskDoneCheck`)가 있어 5초 안에 체크하지 못할 수 있다. 사용자는 "취소"로 멈출 수 있다. 사이클 완료 시의 "수료증 만들기"는 I-004에서 자동 시작 자체를 하지 않기로 해서 카운트다운과 겹치지 않는다.
  - 알림음·브라우저 알림은 지금처럼 세션이 끝날 때 울리고, 다음 세션이 시작될 때 따로 울리지 않는 것으로 가정.
- 처리 메모:
  - 2026-11-08 완료 (f075222)
  - 타이머에 "자동 시작 대기"(`autoStart`) 상태 추가. 세션이 끝나면 다음 세션은 시작 전 상태로 기다리고 시간은 흐르지 않음.
  - 5초는 완료 팝업이 실제로 보인 순간부터 셈 (축하 1초 뒤, 설정·수료증 창이 닫혀 있고, 탭을 보고 있을 때). 시작 시각은 "보인 시각 + 5초" 기준이라 화면 갱신이 늦어도 정확함.
  - 다른 탭에 있거나 자리를 비우면 돌아올 때까지 기다림 (사용자 결정). 카운트다운 중에 자리를 비워 다음 세션 시간까지 지났으면 시작 전 상태로 둠.
  - "취소", X, Esc, 바깥 클릭 = 이번 자동 시작만 취소 (설정은 그대로). "지금 시작" = 바로 시작.
  - 팝업을 아직 못 본 대기는 저장하지 않음 → 그 상태로 새로고침하면 시작 전 상태로 돌아감 (멈춰 있지 않게).
  - 할 일 완료 체크는 한 번 누르면 되어 5초 안에 충분하다고 보고 카운트다운을 멈추지 않음. 수료증은 I-004로 카운트다운 대상에서 빠짐.
  - 2026-11-08: 카운트다운 중 "지금 시작", "취소" 버튼 넣기로 확정.

### I-003 · 설정 창이 열려 있으면 다른 팝업보다 위에 보이게
- 종류: 개선
- 우선순위: 보통
- 상태: 완료
- 등록일: 2026-11-08
- 화면/기능: 설정 창, 세션 완료 팝업(`CompletionDialog`)
- 내용: 설정 창을 보고 있는 중에 세션이 끝나면, 완료 팝업이 설정 창 위에 덮여 뜬다. 설정 창이 항상 다른 팝업보다 위에 있었으면 한다.
- 원인:
  - 모든 팝업이 브라우저 기본 `<dialog>`의 `showModal()`을 쓴다(`src/components/ui/Dialog/Dialog.tsx`). 이렇게 연 팝업은 브라우저의 top layer에 올라가고, **나중에 연 팝업이 무조건 위에** 그려진다. CSS `z-index`로는 순서를 바꿀 수 없다.
  - 반대로 다른 팝업이 떠 있을 때 설정 창을 여는 경우는 없다. 팝업 뒤 화면은 클릭이 막혀 있고, 단축키(S)도 팝업이 열려 있으면 동작하지 않는다(`src/features/shortcuts/shortcuts.ts`의 `dialogOpen`). 그래서 실제로 겹치는 경우는 "설정 창이 열린 뒤 다른 팝업이 새로 뜨는 경우"뿐이다.
- 기대 동작 (제안):
  1. 설정 창이 열려 있는 동안 세션이 끝나면, 완료 팝업은 바로 띄우지 않고 기다린다.
  2. 설정 창을 닫으면 그때 완료 팝업이 뜬다.
  3. 알림음·브라우저 알림은 지금처럼 세션이 끝나는 순간 울린다 (끝난 걸 알 수 있게).
  4. 설정 창 안에서 여는 확인 창(데이터 초기화의 `ConfirmDialog`)은 설정 창 위에 뜨는 지금 동작을 유지한다.
- 관련 코드:
  - `src/features/settings/components/SettingsButton.tsx`: 설정 창 열림 상태(`open`)가 이 컴포넌트 안에만 있다. 완료 팝업이 알 수 있게 공유 상태(스토어 등)로 빼야 한다.
  - `src/features/timer/components/CompletionDialog.tsx`: `open={completed !== null && shown}` 조건에 "설정 창이 닫혀 있을 때"를 추가한다.
- 개발 시 확인할 점:
  - **I-002와 함께 처리:** 자동 시작 카운트다운(5초)은 완료 팝업이 실제로 보인 순간부터 세야 한다. 설정 창이 열려 있는 동안에는 다음 세션이 시작되지 않고 기다려야 한다.
  - 같은 원리로, 앞으로 새로 생기는 자동 팝업도 설정 창이 열려 있으면 기다리게 하는 공통 규칙으로 두면 좋다.
- 처리 메모:
  - 2026-11-08 완료 (f075222, I-002와 함께)
  - 공통 규칙 `useHoldAutoPopups()`(src/lib/popupHold.ts): 사용자가 직접 연 창(설정, 수료증)이 떠 있는 동안 저절로 뜨는 팝업(완료 팝업)을 기다리게 함. 창을 닫으면 그때 뜸.
  - 한 번 뜬 완료 팝업은 그 안에서 연 수료증 창 때문에 닫히지 않음.
  - 알림음·브라우저 알림은 지금처럼 세션이 끝나는 순간 울림.

### I-004 · 사이클을 마치면(수료증 시점) 자동 시작하지 않고 멈춤
- 종류: 개선
- 우선순위: 보통
- 상태: 완료
- 등록일: 2026-11-08
- 화면/기능: 설정의 "휴식 자동 시작", "집중 자동 시작" / 사이클 완료 팝업("한 사이클 완료!")
- 내용: 자동 시작을 켜두면 사이클의 마지막 집중이 끝나도 긴 휴식이 저절로 이어진다. 수료증이 생기는 사이클 완료 시점에는 자동 시작 설정과 상관없이 멈췄으면 한다.
- 기대 동작:
  1. 집중을 `긴 휴식 주기`만큼 마쳐 사이클이 완료되면, "휴식 자동 시작"이 켜져 있어도 긴 휴식을 자동으로 시작하지 않는다.
  2. 이때 뜨는 "한 사이클 완료!" 팝업은 자동 시작이 꺼져 있을 때와 같다: "수료증 만들기", "나중에", "긴 휴식 시작 →". 카운트다운(I-002)은 나오지 않는다.
  3. 사용자가 "긴 휴식 시작 →"을 눌러 긴 휴식을 시작하면, 그 뒤로는 다시 자동 시작 설정대로 동작한다. (긴 휴식이 끝나면 "집중 자동 시작"이 켜져 있을 때 다음 집중을 자동으로 시작)
  4. 사이클 중간의 짧은 휴식, 집중은 지금처럼 자동 시작 설정을 따른다.
- 관련 코드:

### I-009 · 처음 들어왔을 때 사용법 안내 팝업
- 종류: 개선
- 우선순위: 보통
- 상태: 열림
- 등록일: 2026-11-08

- 기대 동작 (제안):
  1. 처음 방문했을 때 한 번만 자동으로 뜬다. 한 번 닫으면 다음부터는 뜨지 않는다.
  2. 3~4장짜리 넘기는 안내. 까미가 함께 나온다. 예:
     - 1장: 까모도로 소개 (집중 25분 → 짧은 휴식 → 반복, 4번 마치면 긴 휴식과 수료증)

     - 3장: 집중 소리, 캘린더, 설정 위치 안내

### I-014 · 로그인 (아이디·비밀번호·닉네임), 로그인 없이도 사용 가능
- 종류: 개선 (큰 작업)

- 상태: 열림
- 등록일: 2026-11-08
- 화면/기능: 회원가입·로그인 화면, 헤더 메뉴(I-011), 로그인해야 쓸 수 있는 기능
- 내용: 간단한 회원가입·로그인을 만든다. 로그인한 사람만 쓸 수 있는 기능을 추가할 예정이다. 로그인하지 않아도 지금처럼 모든 기본 기능을 쓸 수 있어야 한다.
- 기대 동작:
  1. **회원가입:** 아이디, 비밀번호, 닉네임을 입력한다. (이메일·소셜 로그인 없음)
  2. **로그인 / 로그아웃:** 아이디 + 비밀번호. 헤더 메뉴(I-011)에 "로그인" 항목, 로그인하면 닉네임과 "로그아웃".
  3. **로그인 없이 사용:** 지금처럼 브라우저에 저장하며 모든 기본 기능을 쓴다.
  4. **로그인 전용 기능:** 로그인하지 않은 사람에게는 잠금 표시와 "로그인하면 쓸 수 있어요" 안내. (어떤 기능인지는 미정)
  5. 닉네임은 화면 인사, 수료증 이름 등에 쓸 수 있다 (`docs/03-decisions.md`의 "수료증에 이름 넣기 검토"와 연결).
- 기존 결정과 달라지는 점 (개발 쪽에서 문서 반영 필요):
  - `docs/02-mvp-scope.md` "5. 로그인 + 동기화"와 `docs/03-decisions.md` "계정" 항목은 로그인 방법을 "구글, 카카오 등"으로 적어 두었다. **아이디·비밀번호·닉네임 방식으로 바뀜** (2026-11-08 사용자 결정). 두 문서의 결정·변경 이력을 고친다.
  - "로그인 없이도 쓸 수 있게 유지(추천)"는 **유지로 확정**.
- 정하지 않은 것 (시작 전에 정해야 함):
  - **로그인 전용 기능 목록:** 예) 여러 기기 동기화, 기록 백업, 통계 전체 기간, 수료증에 닉네임 넣기 등.
  - **서버/서비스:** Supabase / Firebase / Next.js 서버 + DB 등. 기존 문서상 후보는 Supabase, Firebase.
  - **로그인 전 쌓인 데이터:** 처음 로그인할 때 이 브라우저의 할 일·기록·설정을 계정으로 옮길지(제안: 옮길지 물어봄).
  - **비밀번호를 잊었을 때:** 이메일이 없으면 스스로 찾을 방법이 없다. 관리자(I-015)가 초기화해 주는 방식 / 가입할 때 복구용 이메일(선택) 받기 / 복구 없음 중 선택.
- 개발 시 확인할 점:
  - **순서:** 기존 계획대로 배포(고정 HTTPS 주소) 다음에 한다 (`docs/02-mvp-scope.md` 다음 개발 순서 4 → 5).
  - **비밀번호는 절대 그대로 저장하지 않는다.** 로그인 서비스(BaaS)의 인증 기능을 쓰거나, 직접 만든다면 bcrypt/argon2 같은 해시로 저장한다. 로그인 시도 횟수 제한도 둔다.
  - Supabase·Firebase의 기본 인증은 이메일 기반이다. 아이디로 로그인하려면 아이디를 내부용 이메일 형식으로 바꿔 쓰거나 별도 처리가 필요하므로 서비스 고를 때 확인한다.
  - 아이디·닉네임 규칙: 길이, 쓸 수 있는 글자, 중복 확인, 닉네임 변경 가능 여부.
  - **개인정보:** 계정을 받으면 개인정보처리방침 페이지, 회원 탈퇴와 데이터 삭제 기능이 필요하다 (`docs/03-decisions.md` 공개 범위 2단계).
  - 문구는 I-013(다국어) 대비로 한 파일에 모아둔다.
- 처리 메모:

### I-015 · 관리자 페이지 (사용 패턴 확인)
- 종류: 개선 (큰 작업)
- 우선순위: 낮음 (I-014 로그인 이후)
- 상태: 열림
- 등록일: 2026-11-08
- 화면/기능: 새 페이지 (예: `/admin`), 관리자 계정만 접근
- 내용: 로그인 기능이 생기면 관리자 페이지를 만들어 사용자들이 사이트를 어떻게 쓰는지(사용 패턴) 확인한다.
- 기대 동작 (제안):
  1. 관리자 계정으로 로그인한 경우에만 들어갈 수 있다. 일반 사용자에게는 메뉴도 보이지 않는다.
  2. 볼 수 있는 내용 예:
     - 가입자 수, 날짜별 새 가입자, 날짜별 활동 사용자 수
     - 집중 세션 수·총 집중 시간 (날짜별, 시간대별)
     - 자주 쓰는 설정 (집중 시간 길이, 자동 시작 사용 비율, 집중 소리 종류별 사용)
     - 사이클 완료·수료증 생성 수
  3. 사용자 목록 (아이디, 닉네임, 가입일, 마지막 접속). 필요하면 비밀번호 초기화(I-014 복구 방식에 따라), 계정 정지.
- 정하지 않은 것:
  - **어떤 패턴을 볼지:** 위 예 중 무엇이 필요한지, 개인별로 볼지 전체 합계만 볼지.
  - **로그인하지 않은 사용자:** 로그인 없이 쓰는 사람의 사용 패턴도 볼지. 지금은 데이터가 브라우저에만 있어 서버에서 볼 수 없다. 보려면 익명 사용 통계를 따로 모아야 한다 (예: Vercel Analytics, 직접 이벤트 수집).
- 개발 시 확인할 점:
  - **관리자 권한은 서버에서 확인한다.** 화면에서 메뉴만 숨기면 안 되고, 데이터를 주는 쪽(API, DB 접근 규칙)에서 관리자만 읽게 막는다.
  - **개인정보:** 사용 패턴을 모은다는 것과 그 목적을 개인정보처리방침에 적는다. 개인별 기록을 보는 것보다 합계 위주로 보는 것이 부담이 적다.
  - 관리자 계정을 만드는 방법(처음 1명은 DB에서 직접 지정 등).
  - 차트는 기존 통계 화면 방식과 맞춘다.
- 처리 메모:

### I-016 · 집중 소리에 "비행기 기내" 소리 추가
- 종류: 개선
- 우선순위: 보통
- 상태: 열림
- 등록일: 2026-11-08
- 화면/기능: 집중 소리 선택 창
- 내용: 비행기에 타고 있을 때 들리는 소리(엔진이 낮게 웅웅 울리는 기내 소리)를 집중 소리에 추가한다.
- 기대 동작 (제안):
  1. 이름 "비행기 기내", 설명 "낮게 울리는 엔진 소리" 정도. 아이콘은 비행기.
  2. 다른 녹음 소리와 같은 크기로 들리고, 끊김 없이 반복된다.
  3. 기내 안내 방송, 사람 말소리, 아기 울음, 벨 소리("띵") 같은 튀는 소리가 없는 구간만 쓴다.
- 관련 코드:
  - `scripts/focus-sounds.mjs` + `src/features/focus-sound/recordings.json`: 원본 녹음을 잘라 `public/sounds/<id>.m4a`로 만든다. `recordings.json`에 새 항목 추가 (예: id `airplane`).
  - `src/features/focus-sound/sounds.ts`: `FOCUS_SOUND_IDS`, `FOCUS_SOUNDS`(이름·설명·아이콘·`level`), `FOCUS_SOUND_GROUPS`에 추가.
  - `src/components/icons/icons.tsx`: 비행기 아이콘 추가.
  - `docs/03-decisions.md`의 집중 소리 출처 표: 새 소리의 출처 추가.
- 개발 시 확인할 점:
  - **원본 소리:** 기존 녹음처럼 Pixabay(무료, 상업적 사용 가능)에서 "airplane cabin", "airplane interior" 같은 이름으로 찾는다. 원본은 `design/sound/`에 두고 저장소에는 올리지 않는다 (Pixabay 라이선스상 파일을 그대로 따로 배포하는 것은 금지).
  - **낮은 소리 걸러내기(`lowCut`):** 기내 소리는 대부분 낮은 울림이라, 다른 소리처럼 60~80Hz에서 자르면 특유의 묵직함이 사라진다. 더 낮게(예: 20~30Hz) 잡고 들어보며 정한다.
  - **그룹:** 지금 그룹은 "노이즈"(3개), "자연의 소리"(5개)뿐인데 비행기는 자연의 소리가 아니다. 제안: 새 그룹 "공간의 소리"를 만들고, 나중에 카페·기차 등도 여기에 추가. (한 개짜리 그룹이 어색하면 "노이즈" 옆에 두는 것도 방법)
  - I-007(소리별 배경)을 할 때 이 소리의 배경(비행기 창밖 구름 등)도 함께 정한다.

### B-001 · 탭을 두 개 열면 할 일·기록이 사라지고 타이머가 따로 놂
- 종류: 버그
- 우선순위: 높음
- 상태: 진행 중
- 등록일: 2026-11-08
- 화면/기능: 모든 페이지 (브라우저 탭 여러 개)
- 내용: 탭마다 할 일·기록·타이머를 따로 들고 있다가 저장할 때 자기 것으로 덮어쓴다. 다른 탭에서 추가한 할 일이 사라지고, 한 탭에서 시작한 타이머를 다른 탭은 모른다. 테마도 따로 논다.
- 재현 방법:
  1. 타이머 화면을 탭 두 개(A, B)로 연다.
  2. B탭에서 할 일을 추가하고, A탭에서 할 일을 추가한다.
  3. 새로고침하면 A탭에서 추가한 할 일만 남는다.
- 기대 동작 (2026-11-08 확정):
  1. 한 탭에서 바꾼 할 일·기록·타이머·설정·테마가 다른 탭에도 바로 보인다.
  2. 두 탭이 같은 집중을 동시에 끝내도 기록은 하나, 🐾도 한 번만 올라간다.
  3. 알림 소리, 브라우저 알림, 집중 소리는 마지막으로 보고 있던 탭 하나에서만 난다.
  4. 완료 팝업은 모든 탭에 뜨고, 한 탭에서 닫거나 다음 세션을 시작하면 다른 탭 팝업도 닫힌다.
- 관련 코드: `src/lib/useHydrateStores.ts`(저장값 불러오기), `src/features/timer/store.ts`(세션 완료 처리), `src/features/alerts/`, `src/features/focus-sound/useFocusSound.ts`, `src/features/theme/theme.ts`
- 처리 메모:
  - 나중에 서버 동기화를 붙여도 같은 브라우저의 탭끼리는 저장소를 함께 쓰고 로그인 없이도 쓰므로 필요한 수정. 저장 형식은 바꾸지 않음.
